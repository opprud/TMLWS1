# Exercise 7.1 — Random Forest on features, deployed with emlearn

Train a Random Forest on your Module-5 fan features, convert it to a C header with emlearn, and run features + model live on the RAK4631 with class output on serial and the LEDs.

Because trees compare raw feature values, **no scaling/normalisation is needed** — the features you computed in C in Module 5 feed straight into the model.

```
rf-features/
├── README.md            ← you are here
├── train_rf.py          ← train + convert + export golden test vectors
├── data/raw/            ← put your fan CSVs here: <label>.<nnnnn>.csv
└── platformio/          ← RAK4631 firmware

        ├── feature_scale.h   (generated by train_rf.py — the 13 scale factors)
        └── test_windows.h    (generated by train_rf.py)
```

Converting your Edge Impulse export to CSVs: [`../ei_json_to_csv.py`](../ei_json_to_csv.py) (Step 1).

## Step 0 — Python prerequisites

Use the course venv from the setup guide, with the **pinned** emlearn version
(`pip install "emlearn==0.23.*"` — the pin from setup-guide.md §4, same as Module 6).
The generated headers change between emlearn releases, so everyone must be on the same

## Step 1 — Train and convert (laptop)

1. Get your Module-4 recordings into `data/raw/`, one CSV per recording, named `<label>.<index>.csv` (e.g. `imbalance.00003.csv`) with columns `timestamp,x,y,z`.

   Your data lives in Edge Impulse Studio, which exports the **ingestion JSON** format (one `.json` per sample), not CSV. Export it (**Data acquisition → select all → ⋮ → Export data (JSON)**, or *Dashboard → Export*), then convert with the provided script:

   ```bash
   python ../ei_json_to_csv.py path/to/ei-export/        # dir of .json files, or the .zip itself
   ```

   It writes correctly named CSVs into `data/raw/` by default (`--help` for options). Already have plain CSVs in that format? Just drop them in.
2. Run:

   ```bash
   python train_rf.py
   ```

   Expected output (numbers will differ):

   ```
   Files: 25   Windows: train 348 / test 117  (split by recording, not by window)
   Label order (class index in C): ['blocked', 'imbalance', 'normal', 'off', 'scrape']
   Feature quantisation (train max -> int16):
     std_x      x4096      max|f|=   1.8710 -> q in [   262,   7664]
     ...
     res_mean   x512       max|f|=   9.9135 -> q in [  4823,   5076]
   Test accuracy: 0.99
   [confusion matrix]
   Wrote platformio/src/fan_model.h       (~ 15–60 kB)
   Wrote platformio/src/feature_scale.h   (the 13 scale factors)
   C-vs-Python check: 465/465 windows agree
   Wrote platformio/src/test_windows.h    (one golden window per class)
   ```

3. **Note the label order** — the C code indexes class names in this (alphabetical) order.
4. **Three headers are generated together** — `fan_model.h`, `feature_scale.h`, `test_windows.h`. Never copy one without the others; a stale `feature_scale.h` moves every split threshold silently.

> **Why the features become integers.** emlearn's tree runtime is **fixed-point**: `EmlTreesNode.value` is an `int16_t` (look in `lib/emlearn/eml_trees.h`), and the generated predict is `int32_t fan_model_predict(const int16_t *features, int32_t n)`. Hand it floats and the split thresholds truncate into that integer field — `std_x < 0.42` becomes `std_x < 0`, every comparison is false, and the board reports one constant class. So `train_rf.py` quantises **before training** and the firmware applies the identical scale.
>
> One scale for all 13 features would not work: std/MAD live around 0.03–2, kurtosis spans −1.5…45, RMS and the resultant sit near 10 m/s². Each feature therefore gets **its own power-of-two scale**, chosen so the largest value in the *training* split lands near 8192 — leaving ~4× headroom to `int16`'s 32767 before the firmware clamps. Powers of two are exact in `float32`, so Python and C compute bit-identical products.
>
> Two consequences worth internalising: integer inference needs **no FPU** (this is the Module 9 preview), and the quantisation is now part of the model — `feature_scale.h` is as much "the model" as `fan_model.h` is.

> **Why the accuracy is honest:** `train_rf.py` splits train/test **by source recording** (`GroupShuffleSplit` on the CSV filename), not by window. Windows overlap 50 %, so a plain window-level split would put near-identical windows from the same 20 s recording on both sides and inflate the score — exactly the leakage Modules 4 and 5 warned about. The recording-level split makes the printed accuracy comparable with the Edge Impulse models in the worksheet, which are evaluated on EI's recording-level held-out test set. The scale factors are likewise fitted on the training split only.

> **The `C-vs-Python check` line** compiles the generated header and runs it on every window, comparing against scikit-learn. It must read `N/N agree`; the script exits non-zero otherwise. (It needs a host C compiler — without one the line is skipped and the golden-window tests in Steps 2 and 4 carry the load.)
>
> Two things stand between "converted" and "identical", and they are worth knowing before you trust any converted model:
>
> 1. **Comparison direction.** scikit-learn branches left on `x <= threshold`; emlearn branches on `x < node.value` and writes that value with a **truncating** `int(t)`. With integer features `x <= t` means `x < floor(t) + 1`, so `train_rf.py` rewrites the thresholds accordingly before converting. Skip it and a few samples per forest take the wrong branch — silently, and only on some datasets.
> 2. **How the trees are combined.** scikit-learn averages the *class probabilities* of all 10 trees; emlearn's runtime takes a *majority vote* of their hard labels. Those agree whenever the leaves are nearly pure, which at `max_depth=8` on this data they are (hence `465/465`) — but it is a real semantic difference, not a rounding one, and shallow forests can diverge on it. This is exactly why the check runs on every window instead of trusting the conversion.



## Step 2 — Validate on the laptop (optional but recommended)

If you have `gcc` installed, compile the model + features against the golden windows before going anywhere near the board — this is step 2 of the 4-step ladder. The emlearn headers are already in place (Step 3), so:

```bash
cd platformio/src
gcc -DHOST_TEST -I ../lib/emlearn -o /tmp/hosttest host_test.c -lm && /tmp/hosttest
```

Optional — teams can also skip straight to the on-target static tests (Step 4).

## Step 3 — emlearn headers (nothing to do)

The generated `fan_model.h` does `#include <eml_trees.h>` — recent emlearn versions emit
that even with `method='inline'`. Those runtime headers are **already vendored** in
`platformio/lib/emlearn/`, and `platformio.ini` adds `-I lib/emlearn` to the build flags.
Copying the model header into `src/` (Step 1) is the only copy you need. Module 6's
`xor-device` is set up identically.

> **Where do C headers come from in a Python package?** `pip install emlearn` ships
> emlearn's C runtime *inside* the Python package — `python -c "import emlearn;
> print(emlearn.includedir)"` prints the directory holding them. Worth running once: it is
> the whole train-in-Python/run-in-C idea in one path. We vendor only the three headers the
> model actually pulls in (`eml_trees.h` → `eml_common.h` → `eml_log.h`, 14 KB) instead of
> copying that directory, because `includedir` *is* the package dir — copying it drags 43
> headers **and 46 `.py` files** (≈976 KB of Python) into a microcontroller project, and
> pins the runtime to whatever `pip` happens to hold rather than the version this lab was
> tested against.

## Step 4 — Flash and test with static data

1. Open `platformio/` in VS Code, check `platformio.ini` (board `wiscore_rak4631`).
2. In `main.cpp`, `RUN_STATIC_TESTS` is `1` by default: on boot the firmware runs every golden window from `test_windows.h` through features + model and prints PASS/FAIL. (The static tests run *before* the sensor check, so this step works even without the RAK1904 mounted.)
3. Build & upload. Serial monitor at **115200**:

   ```
   [static] window 'normal'    -> predicted 'normal'    PASS  (feat 812 us, model 41 us)
   [static] window 'imbalance' -> predicted 'imbalance' PASS  (feat 809 us, model 43 us)
   ...
   ```

   A FAIL prints the window's 13 features as `float  ×scale -> int16`. Diff that against `python train_rf.py --print-features`, which prints the same three columns: **floats differing** means the C feature code drifted from the Python one, **floats matching but ints differing** means `feature_scale.h` is stale — regenerate the model and scales together.

   (`feat` now includes quantisation: 13 multiply-round-clamp operations, lost in the noise next to the 500-sample statistics.)

All PASS? You have validated the entire chain except the sensor.

## Step 5 — Go live

1. Set `RUN_STATIC_TESTS` to `0`, rebuild, upload.
2. Mount the board on the fan (Module 4 rig). The firmware samples the LIS3DH at 250 Hz (ODR 400 Hz) into a double buffer and classifies every second (500-sample window, 50 % overlap):

   ```
   normal     (conf n/a)  feat 812 us  model 42 us  total 854 us

   (illustrative — the firmware now enables DWT in setup() so these are real
    measurements at 15.6 ns resolution. Without it micros() steps in 976.5625 us
    on this core, so `model` would read a flat 0 us and `feat` would be quantised
    to a multiple of 977. Numbers also scale with WINDOW_LEN, now 500 not 200.)
   imbalance  ...
   ```

3. LEDs: `LED_GREEN` on = `normal`, `LED_BLUE` on = any fault state, both off = `off`.
4. Provoke each fault state (tape weight, blocked airflow, scrape) and watch the output.
5. Record the latency numbers and the build-summary flash/RAM for the worksheet.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `LIS3DH not found` on serial | RAK1904 must sit in **sensor slot A**; address is `0x18`. The firmware drives `WB_IO2` HIGH to power the sensor rail — if you removed that block from `setup()`, put it back. Power off before reseating. Run an I²C scanner if in doubt. |
| Upload fails / no port | Double-press RESET → bootloader mode (green LED breathes) → upload again. |
| Static tests FAIL | Feature or scale mismatch — a FAIL now dumps `float ×scale -> int16` per feature; diff it against `train_rf.py --print-features`. Kurtosis is the usual suspect on the float side — both sides must use the *biased Fisher* estimator. |
| Everything classifies as one class | Sample rate mismatch (training data vs firmware `SAMPLE_RATE_HZ`), axes swapped vs your recording orientation — or the quantisation is bypassed. If `fan_model_predict` is being handed the **float** array, every threshold truncates to 0 and the forest votes one constant class; it must get `features_q` from `quantise_features()`. |
| Int features all `0` or all clamped at `±32767` | `feature_scale.h` does not belong to this `fan_model.h`. Re-run `train_rf.py` — it writes both. |
| `fan_model.h` / `feature_scale.h`: `No such file` | Run `train_rf.py` first — all three headers are generated, not checked in. |
| Build fails: `eml_trees.h: No such file or directory` | `platformio/lib/emlearn/` is missing its three headers, or `-I lib/emlearn` is not in `build_flags` in `platformio.ini`. Re-pull the repo, or copy the same three headers from Module 6's `xor-device/lib/emlearn/`. |
| Build fails inside `fan_model.h` (narrowing conversion, unknown type, wrong `eml_trees_predict` signature) | Version skew: your `pip` emlearn differs from the vendored runtime (`lib/emlearn/VERSION.txt`, 0.23.2). Re-run Step 0's pinned install and regenerate the model. |
